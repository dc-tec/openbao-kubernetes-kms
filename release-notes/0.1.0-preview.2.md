# Evaluation preview

`0.1.0-preview.2` is for labs, staging, and evaluation. It is not approved for production control planes and does not introduce an LTS or production support commitment.

## Security and reliability changes

- Reject all OpenBao HTTP redirects. Earlier previews could forward OpenBao tokens, login JWTs, or Transit encryption material when an HTTPS endpoint redirected a request. Redirects now fail with a redacted `unavailable` error before the destination receives a request.
- Update the Go toolchain to 1.26.6, gRPC to 1.83.2, and other dependencies to include security fixes accumulated since `0.1.0-preview.1`.
- Bound OpenBao HTTP response bodies and concurrent KMS requests.
- Enforce Transit `disable_upsert=true` during startup and metadata probes.
- Correct metadata/deep-probe health handling and token use, and stabilize the OpenBao HA test fixtures.
- Download the pinned CI security scanner directly from its release with bounded retries and a repository-pinned archive checksum.

## Before upgrading

1. Ensure `openbao.address` serves requests without HTTP redirects. For HA, use OpenBao server-side request forwarding or an endpoint routed to the active node. HTTPS and same-origin redirects are also rejected.
2. Configure the dedicated Transit mount with `disable_upsert=true`. Grant the provider policy `read` on `<transit-mount>/config/keys`, in addition to the documented key metadata, encrypt, and decrypt permissions.
3. Preserve provider registry state, its checkpoint, and identity-bearing configuration. Retain compatible OpenBao and etcd backups.
4. Run the new provider's `doctor` command before upgrading one control-plane node at a time.

KMS v2, key ID derivation, annotations, and AAD formats are unchanged from `0.1.0-preview.1`. The stricter transport and Transit checks can reject deployments that previously started with unsafe or unsupported settings.

## Evaluation scope

The release gate targets OpenBao 2.6.0 and the digest-pinned Kubernetes 1.34 and 1.35 Kind lanes. Public binary and container artifacts use JWT authentication. Other Kubernetes/OpenBao versions and production capacity or availability guarantees are outside this preview's scope.

The release workflow validates OpenBao and Kind integration, failure handling, HA, rotation, restore, upgrade/rollback, and bounded load scenarios. It also checks source/image vulnerabilities, reproducibility, signatures, SBOMs, and provenance. This release does not constitute an independent security audit or renewed qualification of the local kubeadm VM harness.
