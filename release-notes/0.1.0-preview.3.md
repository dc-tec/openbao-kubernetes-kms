# Evaluation preview

`0.1.0-preview.3` is for labs, staging, and evaluation. Do not use it to protect
production control planes. Support remains best effort, with no production
service-level objective or long-term support window.

## Fresh installation required

Use a fresh disposable installation with a new Transit key and provider
identity. In-place upgrades from earlier previews are unsupported. Registry
schema `v1alpha2` binds the configuration identity, including the Transit key
name and mount path. The provider rejects older unbound state without rewriting
its registry or checkpoint. Preserve the old installation and its matching
artifacts; do not delete state, checkpoints, or key material to bypass this check.

Checkpoint validation accepts only the same registry state or its immediate
hash-linked successor. Back up and restore the registry and its checkpoint
together. Keep compatible etcd and OpenBao backups with every Transit key
version that retained ciphertext can need. A recreated Transit key with the
same name cannot decrypt data encrypted with the original key.

KMS key ID derivation, annotations, and additional authenticated data (AAD)
bytes are unchanged. That wire-format continuity does not make old registry
state compatible with this release.

## Security updates

Builds use Go `1.27.3`. The module, development environment, CI, and container
builders use the pinned toolchain. Rebuild provider binaries and images to
include these fixes.

Go `1.27.3` rejects certificate chains containing any of the eight compromised
eMudhra intermediate CA public keys. OpenBao connections use the configured CA
bundle. OAuth token requests use system roots when
`auth.jwt.oauth2.caCertFile` is omitted; setting that field replaces system
roots with the configured bundle. Replace affected certificates before using
the updated provider. Keep TLS verification enabled.

This release also includes the Go `1.27.2` security fixes and updates
`golang.org/x/net` to `v0.60.0` for the October HTTP/2 fixes. These updates do
not change the separate OpenBao or Kubernetes API server binaries. See the
[Go security fix](https://github.com/golang/go/issues/82345),
[Go release history](https://go.dev/doc/devel/release#go1.27.3), and
[HTTP/2 advisory](https://pkg.go.dev/vuln/GO-2026-6617).

## Authentication

The provider can obtain signed JWT access tokens through native OAuth 2.0
client credentials and exchange them for OpenBao tokens. Select
`auth.jwt.source: oauth2` and configure either `client_secret_basic` or
`client_secret_post`. The issuer, its storage, DNS, routing, TLS trust, and
client-secret provisioning must work while the protected API server is down.
Opaque access tokens and interactive flows are outside this integration.

Existing file JWT configurations can omit `auth.jwt.source` only when
`jwtFile` is set and no `oauth2` section is present. Empty source values and
mixed file/OAuth settings fail validation. OAuth authentication never falls
back to a JWT file or another authentication method.

OAuth and OpenBao tokens remain in memory. OpenBao token renewal does not
request another OAuth token; an issuer outage can leave an existing OpenBao
token usable. New logins require the issuer. Disabling an OAuth client does
not revoke OpenBao tokens already issued to it. The client-secret file is
reread before each grant, so atomic replacement supports credential rotation.

## Installation and artifacts

`init` generates matching provider configuration, policy, OpenBao setup,
installation records, and per-node `node-setup.sh` scripts. Review generated
files before applying them. Stage the new KMS reader on every API server
before enabling KMS writes. Importing an existing encryption configuration or
retiring its previous readers remains outside this onboarding procedure.

Architecture-specific systemd and static-pod kits include the matching host
binary. The static-pod kit records the provider image digest. Linux control-plane
nodes can use systemd or kubelet static pods. A DaemonSet inside the protected
cluster remains unsupported.

The release includes macOS `amd64` and `arm64` binaries for workstation CLI
commands such as `init` and `policy`. They do not run the provider service;
`serve` refuses to start outside Linux.

New file-JWT static-pod scaffolds mount a dedicated credential directory
read-only so atomic JWT replacement remains visible. Existing file mounts are
not changed automatically. The file-mount correction does not provide a
migration from an earlier preview's registry state.

## Rotation and recovery

Pending versions can decrypt but cannot encrypt before promotion. A restart or
recovery from an unconfirmed observation save restarts the full activation
delay. Local elapsed time bounds token leases, cached status, and retry
cooldowns; a backward clock correction cannot restore an observed expired lease
or status result.

`retire-versions` removes reviewed historical identities from local decryption.
`restore-versions` can restore selected removed records while the matching
Transit versions remain decryptable. Applying either plan requires the
provider to be stopped and the exact reviewed `--expected-state-hash`.
Apply retirement consistently on every node before raising OpenBao minimum
versions. Retained etcd backups can still need those versions.

Removed identities stay in hashed state and do not reappear during normal
rotation. Older binaries that do not understand these records reject the state.
Do not downgrade or erase the records to bypass that rejection. State mutation
and `serve` share a writer lock, and the state directory must be owned by the
provider's OS user.

## Configuration and CLI changes

Configuration validation rejects implicit scalar coercion, invalid Transit key
names, a probe interval at or above the status staleness window, a renewal
increment at or below the refresh lead time, and duplicate fixed health and
metrics endpoints. Preserve identity-bearing values rather than renaming them
to bypass validation.

Invalid command usage returns exit code `2`. Unreadable or malformed
configuration returns `3`; diagnostic failures remain `4`, and runtime
failures remain `5`. Update scripts that previously matched the unclassified
exit code `1` for usage or configuration errors.

## Qualification scope

The candidate qualification targets the eight digest-pinned combinations of
OpenBao `2.7.0` and `2.6.3` with Kubernetes `1.34.11`, `1.35.8`, `1.36.4`, and
`1.37.0`. The tagged release workflow runs OpenBao integration suites against
both OpenBao versions and the four Kubernetes lanes using the primary OpenBao
version. These are separate checks; the tagged workflow does not repeat every
cross-pair. The Transit profile is `aes256-gcm96`. KMS v1, other Transit key
types, external Transit keys, unlisted versions, production availability, and
performance guarantees are outside this scope.

Tagged installation checks validate the selected archives and native packages,
including `init`, `node-setup.sh`, file ownership, and reinstallation. The
separate Provider Qualification workflow checks live generated-kit acceptance
with three API servers.

The exact tagged artifacts must pass the required integration, installation,
recovery, reproducibility, vulnerability scanning, signature, SBOM, and
provenance checks before publication. A passing build or earlier candidate
qualification does not qualify different release artifacts or an adopter's
platform.
